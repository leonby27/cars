# Подготовка фотографий

## Полные галереи просмотренных машин — подготовлено 10.09.2026

После установки обновления через `deploy/install-photo-store.sh` отдельная служба
`abcars-gallery-store.service` сохраняет **все** фотографии просмотренной машины:
каждую в 600px и в оригинальном размере. Они лежат в `/srv/abcars-media` и отдаются
как `STORED`, без вытеснения временным кэшем. Существующая служба каталога продолжает
копировать первые пять 600px кадров каждой активной машины (старые описания только
обложек ниже устарели).

Источник очереди — уже зарегистрированные `vehicle_view` с `human=true` за семь
дней, включая быстрый просмотр. Опрос раз в минуту, без ограничения на 100 самых
популярных машин. Просмотры, которые не попали в аналитику, не запускают копирование.
Первая установка подхватывает предыдущие семь дней; при большом накоплении обработка
идёт в очереди. Это подготовка следующих открытий, не гарантия мгновенного полного
качества при самом первом открытии во время сбоя источника.

Очередь и завершённые просмотры сохраняются в `runtime/photo-store/galleries.json`.
Повторы начинаются через минуту, затем через две, четыре и так далее до часа.
Новый просмотр не сбрасывает задержку после ошибки. Уже сохранённые файлы повторно
не скачиваются; снятые объявления пропускаются. Даже если просмотр стал старше
семи дней, незавершённая очередь остаётся. По два запроса одновременно, низкий
приоритет процесса, остановка ниже 5 ГБ свободного места; служба пробует запуститься
снова через пять минут. Очистка снятых объявлений распространяется на все размеры
галерей по прежним правилам. База данных только читается, новых таблиц нет.

Диагностика каждого запроса фото: `/var/log/nginx/abcars-photos.log`, JSON по строке.
Поля `status`, `upstream_status`, `upstream`, `connect`, `headers`, `response`,
`seconds`, `cache` различают ошибку источника, ожидание соединения/ответа и готовую
копию. Не записываются IP посетителя, cookies, referrer или параметры URL.
Файл подпадает под стандартную ротацию nginx `/var/log/nginx/*.log`; при установке
на другой сервер проверить его правило logrotate.

После разрешённой публикации: установить служебные файлы обычным
`bash /srv/abcars/deploy/install-photo-store.sh`, проверить обе службы, журнал
галерей и новые строки фотодиагностики. Обычная публикация сайта сама службы не
обновляет. Проверить пример `/cars/58933390`: очередь должна завершить 26 адресов
(13 превью + 13 оригиналов), затем каждый ответ должен содержать `X-Photo-Cache: STORED`.
Количество файлов и занятое место проверять отдельно от факта запуска службы.

## Постоянные копии — текущая схема с 07.09.2026

`abcars-photo-store.service` постоянно копирует только обложки всех активных машин
в одном размере каталога (600px) в `/srv/abcars-media/photo/escimg/…`. Эти файлы
не вытесняются. Раз в час служба берёт текущую витрину главной (до 60 машин)
и до 100 самых просматриваемых машин за семь дней и сохраняет первые пять превью.
Они обрабатываются по пять машин между пакетами обложек. Главная случайная:
это подготовка текущей выборки, а не гарантия покрытия каждой будущей выдачи.
Остальные превью загружаются существующей браузерной фоновой очередью рядом с
экраном и остаются в nginx-кэше. Большие фото сохраняются в этом же временном
кэше по запросу, не скачиваются массово. Временный кэш может вытеснять файлы. nginx сначала ищет постоянную копию (`X-Photo-Cache: STORED`),
а за отсутствующим кадром обращается через прежний прокси. Адреса не изменились.

Служба между пакетами старого каталога выбирает новые объявления по first_seen_at
и обрабатывает их приоритетно. Она не задерживает публикацию новых объявлений:
до копирования возможен прежний запрос через прокси. Прогресс и отложенные повторы
сохраняются в `/srv/abcars/runtime/photo-store/progress.json`; база только читается.
После полного прохода копии перепроверяются ежедневно, без повторного скачивания
существующих файлов. Пустые, ошибочные и не-WebP ответы не сохраняются.

Старая суточная и частая службы прогрева выключены, чтобы не конкурировать с
постоянным копированием. Временный nginx-кэш уменьшен до 8 ГБ. При свободном месте
менее 5 ГБ копирование останавливается с ошибкой и повторяется через 5 минут.
Постоянные файлы снятых машин очищаются еженедельно по правилам ниже; рост диска всё равно нужно контролировать.
Первоначальная оценка для двух размеров (600/900) была 18.3 ГиБ;
после решения оставить только 600px объём уменьшится. Это была оценка по выборке,
не гарантия фактического размера. Первый проход занимает часы или дни.

Установка/обновление: после разрешённой публикации выполнить на сервере
`bash /srv/abcars/deploy/install-photo-store.sh`. Служба запускает отдельную копию
кода из `/opt/abcars-photo-store`, поэтому обычный деплой сайта её не обновляет.
При данной задаче служба и nginx уже установлены отдельно по просьбе о копировании.
Проверять журнал службы, progress.json, место на диске и ответ STORED на /photo/.

С 07.09 превью каталога используют только 600px. Новое копирование создаёт максимум
один файл для обычной машины и до пяти для приоритетной вместо десяти. Уже сохранённые 900px не удаляются, прогресс
не сбрасывается: все ранее завершённые машины уже имеют вариант 600px.

## История оптимизаций (предыдущие размеры кэша и таймеры ниже устарели)

Каталог: клиент заранее готовит обложку и четыре дополнительных кадра ближайших
карточек в пределах полутора экранов (600–1600px). На главной упреждение остаётся
300px. Видимые карточки получают более высокий приоритет, чем соседние; выбранный
курсором кадр — высший. Из четырёх мест очереди одно зарезервировано для явного
выбора, чтобы он не ждал завершения четырёх фоновых загрузок. Запросы карточек,
покинувших область подготовки, отменяются до запуска. Упреждение отключено на
сенсорных устройствах без hover, при экономии трафика и на 2G. Фото не уменьшаются
в качестве; переключение ждёт их загрузки и декодирования, сохраняя предыдущий кадр.

Замеры 07.09.2026 с рабочей машины, 12 запросов к первым двум снимкам двух
объявлений из `/api/cars?limit=3&sort=newest`: HIT 77 мс; 11 MISS — 884–1987 мс.
Это время получения конкретного файла, не всей страницы. Мобильная лента
запрашивала 500px, а ночной прогрев готовил 600/900/original только обложки.

Мобильная лента теперь использует 600px, как плитка и подложка галереи.
Большие снимки сохраняют исходное качество. Активный кадр получает высокий
приоритет; миниатюры — низкий. Наведение на полосу миниатюр больше не запускает
40 запросов сразу. В полноэкранной галерее немедленно запрашивается выбранный
кадр, остальные загружаются по мере приближения к ним, включая кадры перед ним.

При наведении мыши на карточку дольше 150 мс или фокусе с клавиатуры заранее
загружается и декодируется оригинал её обложки. Касание/клик повышает приоритет
того же запроса. Фоново одновременно готовятся не более двух обложек; экономия
трафика и 2G отключают упреждение. До открытия всего каталога оригиналы не
запрашиваются. Соседние кадры в галерее теперь ждут загрузки главного или явного
перелистывания: прежний двухсекундный таймер создавал конкуренцию на медленной сети.

Локальная версия тоже использует публичный `/photo/` на abcars.by: прежний Vite
прокси обращался прямо в Китай, обходя готовые копии. На контрольном оригинале
113 КБ первый локальный запрос занял 2842 мс, готовая серверная копия — 60 мс.
Cookie, Authorization и Referer локального запроса не пересылаются. Это изменение
касается только разработки; на опубликованном сайте фотографии по-прежнему
обслуживаются nginx. Для совершенно нового файла остаётся ожидание источника.

Проверка обходов 07.09: в локальном снимке `listing_media` найдено 2 068 314 ссылок, все на
erscglobal2.autoimg.cn. Прямой путь оставался в миниатюрах аналитики, обработчике
ошибки изображения, статическом превью с нестандартным BASE_URL, фотографиях
Guazi в серверной разметке и обложках статей для соцсетей. Теперь интерфейс,
аналитика и генератор разметки используют `src/photo-source.js`: Che168 через
`/photo/`, Guazi через `/api/image`. Запасной размер тоже идёт через сервер и
сбрасывает srcset. Сырые ссылки в данных каталога остаются адресами источника,
но перед отображением преобразуются. Импортёры и серверный прокси продолжают
обращаться к источникам — это заполнение нашей копии, не запрос браузера посетителя.

Ночной `abcars-warm.timer` сохраняется: три размера обложки всего каталога.
Дополнительный `abcars-warm-recent.timer` запускает ограниченный четырьмя потоками
проход, затем ждёт 15 минут до следующего. Выбираются активные объявления,
появившиеся **у нас** за 48 часов (`first_seen_at`, не дата продавца): первые пять
снимков в размерах 600/900/240, первые три также в исходном качестве — максимум
18 файлов на машину. Новейшие объявления обрабатываются первыми. Перекрытие
окна повторяет неудачные запросы. Таймаут 40 секунд включает получение тела;
HTTP-ошибки, пустые ответы и HTML означают неуспешный прогрев.

Кэш остаётся ограниченным 20 ГБ; дополнительная подготовка расходует место в
этом же лимите, старые невостребованные файлы вытесняются. Полный первый проход
может быть долгим. Это не гарантия мгновенного появления каждого кадра:
недавно добавленная машина до прохода, старые непосещённые кадры и вытесненные
копии всё ещё требуют обращения к источнику. Объём скачанного и ошибки видны
в журнале службы.

## При следующей разрешённой публикации

Обычный деплой не устанавливает службы и nginx-сниппеты. После публикации кода:

```sh
install -m644 /srv/abcars/deploy/abcars-warm-recent.service /srv/abcars/deploy/abcars-warm-recent.timer /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now abcars-warm-recent.timer
install -m644 /srv/abcars/deploy/nginx-abcars-photo-location.conf /etc/nginx/snippets/abcars-photo-location.conf
nginx -t && systemctl reload nginx
```

Изменение nginx исключает годовое браузерное кэширование ошибочных ответов.
Проверить журнал нового прохода, активность обоих таймеров, размер/вытеснение
кэша и HIT у подготовленных фотографий. Проверка базы при разработке — только
чтение; тесты прогрева используют отдельный локальный HTTP-сервер.

## Еженедельная очистка снятых машин

`abcars-photo-cleanup.timer`: воскресенье 03:30 UTC / 06:30 Минск, с задержкой
до 15 минут. Отдельная служба не останавливает копирование. База только читается.
Отдельной даты снятия в базе нет: `cleanup.json` запоминает первое наблюдение
статуса unavailable; удаление возможно только через семь полных суток.
Первый запуск лишь начинает отсчёт. Изменение last_seen_at или возврат в active
сбрасывает ожидание. При недельной проверке фактическая задержка может быть больше
семи дней; last_seen_at не считается датой снятия.

Для каждого файла проверяются все ссылки listing_media, включая кадры за пределами
первых пяти и варианты 600/900/original. Любой активный, неизвестный или недавно
снятый владелец защищает файл. Перед удалением владельцы перечитываются.
Файлы без известного владельца, временные файлы и символические ссылки не удаляются;
изменённый после начала проверки файл также пропускается. Nginx-кэш в 8 ГБ живёт
по собственным правилам и этой задачей не очищается.

Проверка без удаления: `node scripts/cleanup-catalog-photos.mjs`.
Реальное выполнение: `systemctl start abcars-photo-cleanup.service`.
Журнал содержит количество кандидатов, удалённых файлов и освобождённых байт.
Первое выполнение с --apply записывает наблюдения даже при отсутствии кандидатов.

## Сбой источника 09.09.2026

Во время открытия /cars/59349947 источник переставал отвечать: nginx фиксировал
таймауты чтения, CDN отдавал 502. Размеры 240px и оригиналы позже восстановились.
Постоянные 600px копии продолжали работать. `proxy_cache_valid any 1m` сохранял
ошибки, которые затем отдавались как STALE. Теперь `proxy_no_cache` разрешает
запись только при статусе 200 и Content-Type image/*; сохранённые успешные фото
по-прежнему доступны при сбое источника. При установке нужно обновить оба файла:
`nginx-abcars-photos-cache.conf` и `nginx-abcars-photo-location.conf`, проверить
nginx и удалить только ранее закэшированные HTTP-ошибки из временного фотокэша.
Постоянные фото и успешные записи временного кэша сохраняются.

Миниатюры галереи используют общий размер 600px. При ошибке загрузчик пробует
размер из объявления, оригинал и 600px, без повторения уже неудачных адресов.
Проверено на изолированном nginx: повторные 502 всегда MISS, восстановление
сразу даёт 200, успешный снимок отдаётся как STALE при следующем сбое источника.
