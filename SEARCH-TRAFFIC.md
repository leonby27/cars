# Поисковые отчёты внутренней аналитики

`/analytics` → «Поисковики»: сумма кликов Google и Яндекса, отдельные счётчики, запросы каждого поисковика и страницы входа с фильтром. Кнопки периода сохранены: сегодня, вчера, 7/30/90 дней.

## Дневной архив

Источники: Google Search Console и Яндекс Вебмастер. В Метрику и GA4 для этих отчётов не обращаемся.

Сборщик загружает статистику каждые шесть часов и сохраняет снимки по ключу **источник + ресурс сайта + дата** в `search_traffic_daily`. Повторный импорт заменяет снимок дня целиком: клики не удваиваются, исправленные значения и удалённые строки обновляются. Старые дни остаются в архиве, даже когда вышли из окна внешнего API. Сброс собственных событий CRM не затрагивает поисковую историю. `search_traffic_sync` хранит дату последнего успешного сбора и обезличенное состояние ошибки.

- Google: первое чтение и обновление старого архива до формата с позициями — за 180 дней (включая предыдущий период для сравнения), последующие — за 14 дней; после перерыва окно расширяется до 180 дней. API скрывает часть запросов. Список дат/общие клики, запросы и страницы читаются отдельными отчётами. Скрытые запросы не уменьшают общий счётчик.
- Яндекс: выгружаются все страницы пагинации запросов и URL за доступное API окно (две недели). Клики считаются по полной выгрузке URL, включая переходы со скрытыми запросами. Для 30/90 дней складываются сохранённые суточные снимки.
- Последние дни могут уточняться. Не полученные от источника даты не считаются нулевыми; интерфейс показывает доступный диапазон и число дней. У Google нулевые промежуточные дни восстанавливаются только до фактически полученной даты, без выдуманных нулей в ещё не опубликованном конце периода.
- Для дневных отчётов 7/30/90 означают столько календарных дат, включая текущую дату по Минску. У Google границы суток в тихоокеанском времени, у Яндекса — московском. Пересчитать дневные запросы в точное скользящее почасовое окно CRM невозможно; это отмечено в сводке.
- В таблицах показано до 1000 наиболее частых строк за период; в архиве остаётся вся полученная выгрузка. При достижении защитного лимита пагинации сбор считается неудачным и прежний снимок сохраняется.
- Авторизованный GET `/api/analytics/search-traffic` только читает архив. Он не ждёт внешние API и не меняет данные. Ошибка сборщика сохраняет предыдущую историю.

## Показы и позиции

В ежедневных строках запросов и страниц сохраняются клики, показы и средняя позиция; снимки отмечены `metricsVersion:2`. Позиция периода — сумма (дневная позиция × показы) / сумма показов. Нулевые/отсутствующие позиции и старые снимки без показов дают `null`, а не выдуманный ноль. Строки с показами без кликов остаются в таблице; сортировка по кликам, затем показам.

Изменение позиции = предыдущая позиция минус текущая: положительное значение означает рост. Сравнение с предыдущим периодом той же длины использует одинаковый опубликованный префикс дней (если из 7 дней доступны первые 6, сравниваем с первыми 6 днями предыдущей недели). Внутренние пропуски дат, отсутствие старого архива или позиции запроса отключают сравнение. Даты сравнения и задержка источников указаны в интерфейсе. Старые снимки обновляются только в пределах доступного API окна; недоступная история не удаляется.

## Настройка доступов

Секреты — только в закрытом серверном окружении, без префикса `VITE_`. Не коммитить и не передавать браузеру. Локально `.env.local` / `.env`, в рабочем окружении существующий `/srv/abcars/.env.local`.

Яндекс: OAuth-токен с правом чтения Вебмастера (`webmaster:hostinfo` и `webmaster:verify`), аккаунт с подтверждённым доступом к сайту.

- `YANDEX_WEBMASTER_TOKEN` — токен.
- `YANDEX_WEBMASTER_HOST_ID` — точный ID ресурса, обычно `https:abcars.by:443`.
- `YANDEX_WEBMASTER_USER_ID` — необязателен, получаем через `/v4/user`.

Для Google также поддерживается `GOOGLE_SEARCH_SERVICE_ACCOUNT_JSON`: ключ сервисного аккаунта без ролей Cloud IAM, которому выдан ограниченный доступ только к abcars.by в Search Console. Этот способ не требует OAuth consent screen и refresh token.

Google OAuth (альтернатива): включить Search Console API в Google Cloud, настроить OAuth-клиент, авторизовать аккаунт с доступом к ресурсу с областью `https://www.googleapis.com/auth/webmasters.readonly` и `access_type=offline`.

- `GOOGLE_SEARCH_CLIENT_ID`, `GOOGLE_SEARCH_CLIENT_SECRET`, `GOOGLE_SEARCH_REFRESH_TOKEN`.
- `GOOGLE_SEARCH_CONSOLE_SITE` — **точное имя** доступного ресурса: `sc-domain:abcars.by` либо `https://abcars.by/`, согласно Search Console.
- Связь GA4 с Search Console не предоставляет нашей интеграции API-доступ. Для постоянной работы проверить режим OAuth-приложения: refresh token внешнего приложения в Testing может истекать через семь дней.

## Включение на действующем сервере

После разрешённого развёртывания и настройки доступов:

1. Применить новую недеструктивную миграцию `031_search_traffic.sql` установленным механизмом миграций.
2. Один раз запустить `node scripts/sync-search-traffic.mjs` в `/srv/abcars`.
3. Установить `deploy/abcars-search-traffic.service` и `.timer` в `/etc/systemd/system/`, выполнить `systemctl daemon-reload` и `systemctl enable --now abcars-search-traffic.timer`.
4. Проверить состояние таймера и сводку. Запущенные одновременно сборщики блокируются advisory lock, снимки сохраняются в транзакции.

Публикация сайта сама по себе не устанавливает новый systemd-таймер; этот шаг обязателен при развёртывании. PostgreSQL — действующее производственное хранилище. Sites-сборка сохраняет совместимость и читает ту же схему архива через D1, если архив перенесён в эту среду; расписание производственного сбора обслуживает серверный таймер.

Проверки: `node --test tests/search-traffic.test.mjs tests/analytics.test.mjs tests/metrika.test.mjs`, `npm run build`, `npm run test:sites`.
