# Prototype Instructions

Talking to the user: he is not a programmer. He sets the goals and makes the product calls, but
he does not read code and does not know the vocabulary. Work at full depth; explain in plain
words. Say what a change means in practice — what a visitor sees, what breaks, what it costs —
not how it works inside, unless he asks. Keep commit hashes, test names, function and variable
names, code snippets and command output out of the prose (file links are fine, they are
clickable). Give any command he needs to run whole, ready to press. When a choice is his,
describe the options by their consequences and say which one you recommend. He checks the
visual result himself in the browser, so a passing build and request-level checks are enough.

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

Typography preference: prioritize comfortable readability over ultra-compact UI. Reading copy — body text, article prose, descriptions, anything a visitor actually reads — stays at 16px or larger. There is no project-wide minimum beyond that (the owner retired it on 2026-08-20, and `tests/typography.test.mjs` no longer checks sizes): service labels, badges, counters, dates and other chrome may be smaller where it reads better, and the sizes recorded elsewhere in this file are the decisions, not exceptions to a rule. Match the “Срок доставки до Минска” label typography to the “Основная информация” label instead of uppercasing it.

Authentication modal preference: present login and registration as a centered modal over the current page without changing its scroll position. Keep only a centered heading above the tabs, with no eyebrow or supporting description. Use darker dark-theme inputs and tab rail, and give the close control a lighter circular surface. Animate the modal's height smoothly when switching between login and registration. Keep the registration consent selected by default and its sentence compact enough for one desktop line with plain underlined links; the consent line is deliberately small.

Vehicle estimate density preference: in the detail sidebar, lead the estimate with the final landed-price figure aligned left and do not label it “Итого” or show a “Предварительный расчёт” heading. Keep intermediate labels and prices slightly smaller, omit dividers between them, and render the non-offer disclaimer as an extra-small plain text line without an icon.

Russian typography preference: prevent short Russian prepositions and conjunctions from hanging at the ends of lines throughout the rendered interface, including dynamic content. Keep the shared typography processor enabled instead of relying only on manually inserted non-breaking spaces.

Brand color preference: use red `#EE1C25` for brand accents, links, icons, and active states instead of orange. Use yellow `#F4D90E` with dark text for all regular primary CTA buttons. Preserve red for destructive actions where it communicates danger.

Outline color preference: never use red for borders, outlines, focus rings, or selection rings anywhere in the product. Keep red for text, icons, fills, and semantic danger accents only; use the shared neutral `--focus-ring` token for accessible focus indication.

Select-search focus preference: keep the search field inside an open select to one thin neutral 1px border only. Do not add an outer focus shadow or a second ring; use `--line-strong` for the focused border.

Select opening-focus preference: opening any searchable select must keep focus on the select trigger instead of automatically focusing the search field; users may focus search explicitly by tapping it or navigating to it with the keyboard.

Favicon preference: use a compact red `#EE1C25` favicon with a centered lowercase white `e` rendered as the Comfortaa 700 glyph from the customer-facing wordmark.

Vehicle gallery preference: clicking the main image should open an immersive modal with a vertical photo stream similar to Auto.ru. On desktop, keep a sticky left-side thumbnail rail for quick navigation and expose the full thumbnail set; on mobile, support horizontal swipe navigation directly on the main gallery. Keep the inline gallery’s previous/next arrows dark on their translucent white circular buttons in both themes so the icons remain legible over photos.

Gallery modal header preference: keep the vehicle title/count close to the left edge and the close control close to the right edge with a compact, symmetrical safe inset instead of centering them to the narrower gallery content width.

Visual QA preference: do not run browser-based visual checks, take implementation screenshots, or perform design-QA comparisons unless the user explicitly asks. The user reviews visual changes manually. Validate changes with build, tests, and non-visual checks only.

Che168 bulk-import preference: run **import v2** — `npm run importv2` (`scripts/import-v2.mjs`), documented in `IMPORTER.md`. It solves the bot challenge once in Playwright Chromium and then reads the site's own React Flight endpoint (`RSC: 1`), where `brandid` and `page` are honoured server-side; discovery and detail reads run concurrently and every `--batch` accepted cards are written to both the static catalog and PostgreSQL. Reach for the v1 DOM-scraping runner (`scripts/import-che168-browser.mjs`) only if that endpoint stops answering. The guidance below describes v1 and still applies to it: use the **Incomplete Reports** catalog and treat client-rendered listing cards as the discovery source of truth; the plain SSR/embedded list payloads may be stale or repeated (the Flight responses paginate honestly, so v2 does not need the sort-order recovery trick). Discover by brand, split large brands into model/series feeds when that improves coverage, use the site's `page` parameter/client pagination, and deduplicate every candidate by the external listing ID. Use multiple sort orders only to recover listings that normal pagination does not expose. After discovery, parse detail cards in parallel and keep the 2020+, pure-electric import policy. Import counts are approximate targets: a slightly larger or smaller valid batch is acceptable. For routine bulk imports, skip browser visual QA and the full test suite unless explicitly requested; run only fast syntax, data-integrity, static-catalog/PostgreSQL count, and relevant parser checks. The user will inspect the rendered catalog visually.

Interaction motion preference: use subtle, immediate microinteractions without delay. Keep select/dropdown, accordion, burger-menu, caret, and currency-switch motion in the 140–200ms range with gentle fade, short translate/scale, or rotation; avoid layout jumps and honor `prefers-reduced-motion`.

Primary loading-state preference: use a compact spinner and short muted label centered in the available viewport instead of an oversized text-based loading hero.

Unfinished-section preference (owner decision, 2026-08-27): a section that takes weeks to finish lives on the main branch behind a switch in `src/feature-flags.js`, not on a side branch. Each flag carries two values — `local` (the `npm run dev` version, normally true so the owner can review without setting anything) and `production` (false until the section ships). The switch must hide the section everywhere at once — home-page block, footer link, client routes (404 when off), generated pages and sitemap — so the site can be deployed at any moment without exposing unfinished work. Keep a test asserting the `production` value is still false, so the section cannot ship by accident. The blog (`BLOG_ENABLED`, `/blog`) is the first section built this way.

Blog preference (owner decision, 2026-08-27): the journal opens with collections («Подборки»). A collection is three layers — evergreen text in `src/blog-texts/`, a selection rule (catalog filters) in `src/blog-posts.js`, and figures pulled from the catalog at render time; never hard-code counts or prices into the text. Four collection cards sit on the home page between the FAQ block and the footer with a «Смотреть всё» link to `/blog`; the journal itself is articles on the left and a section menu on the right. Cards carry cover, category tags, title, and a bottom row with a bare date on the left and a share control on the right — no description, no stock counts, no «Подробнее» affordance, no «Дата:» prefix, no lead paragraph above the grid. The whole card is clickable via a transparent stretched link, so any control inside it must sit above that layer; card corners are clipped on the cover, never with `overflow:hidden` on the card, or the share menu gets cut off. The same share control sits in the top-right corner of an article panel, where its menu opens downward instead of up. The share menu offers copy-link, Telegram and Threads as plain outbound links — never third-party share scripts or counters, which cost weight and track the visitor. It reuses the site select's `.select-menu` / `.select-options` styling (only its position is overridden) so its dark-theme hover states come for free; the select option selectors were widened to `:is(button, a)` for that. The share button uses the round `ShareNetwork` glyph (a tray-and-arrow icon reads as harsh corners in a small circular button), carries an `ActionTooltip` reading «Поделиться» that is dropped while the menu is open, and must be listed in the `corner-shape: round` set, or the squircle rule turns the circle into a rounded square. Menu entries never show link underlines — buttons and links must look identical in the list. Category tags sit on the cover photo, bottom-left, with the same translucent blurred plate as the price and mileage chips on car photos, at 14px/600. The journal's own title and description must stay broader than collections — articles, news and legal explainers are coming to the same page. Tags and date are 14px on every screen size, tags at regular weight (owner decision, 2026-08-27). Tags are derived, never typed by hand: the rubric plus the powertrain the selection rule filters on, with extra taxonomy slugs allowed via `tags: []`, and every tag name must exist in the sidebar menu. The card title is clamped to two lines with an ellipsis; write names that fit, the clamp is a guard, not the normal state. One grid governs the whole journal (owner decision, 2026-08-27): four equal columns inside `page-width` with a 16px gap — home shows four cards, the journal index three cards plus a sidebar exactly one card wide, an article three columns plus that same sidebar. Express it as `repeat(4, minmax(0,1fr))` with `span 3` / `span 1`, never as pixel widths, so every column edge lines up across the three pages at any viewport. The journal index reuses the home cards rather than a list of rows, and both journal pages carry the catalog's `page-width` and breadcrumbs. An article's text sits on its own panel, the same treatment as a model review (dropped on mobile). In the dark theme that panel — and the same panels on model reviews, calculator pages and catalog-section texts — uses `--header-control-bg`, the sidebar's own tone: `--surface` read as a bright slab against the near-black page (owner decision, 2026-08-27). Plates nested inside those panels step up from that tone by the same amount they used to, so reducing the panel's contrast reduces theirs. Inline links inside article prose are accent-coloured with no underline until hover — the browser's default underline breaks the serif line and its visited purple sits outside the palette. The panel keeps its three-column width, but the reading column inside it is capped at the model-review measure (780px — their 860px block less its 40px padding) and centred, so no line runs the full panel width. Articles must not be walls of text. Every article opens with a photo directly after its lead and before the first paragraph — the same frame the material's card shows, so the visitor lands on the car they clicked; it is derived, never authored. Every car in an article — the opening photo, the in-text photos, the grid below — opens in the quick-view modal, honouring the visitor's own toggle: when they switched it off anywhere on the site, or the screen is narrow, the same click opens the full car page instead. Further photos go between sections (never repeating the cover), captioned with its mileage and landed price and linked to the listing — illustration and merchandising in one, and it refreshes with the catalog. Ask the photo store for a frame that matches how large it is shown: display width × 2 for retina, via `srcset` so ordinary screens keep the light file, with the second frame capped at 1400 (the width the photo cache already holds). List cards stay at 600 — they are already 2× — so page weight does not grow where sharpness would not show. The sidebar is two blocks: one flat selector — «Все материалы», then powertrains (Электромобили/Гибриды/Бензиновые), then rubrics (Подборки/Статьи/Новости/Законы/Лайфхаки) — and below it the calculators as separate neutral icon buttons, since they are not journal filters, closed by a yellow «Каталог авто из Китая» button with a trailing arrow that opens the catalog in a new tab (a plain link, not an in-app navigation, so the material the visitor was reading stays open). The four calculator pages carry that same sidebar (with the page you are on marked) so navigation survives the journal → calculator → journal trip; there the panels fill the grid column instead of being narrow centred cards, the reading column inside them is capped at the article measure (780px) so every edge lines up with a journal article, everything including «Другие расчёты» and the disclaimer lives inside that column, and the round back button gives way to breadcrumbs. All of that is behind `BLOG_ENABLED`, so the live calculator pages keep their current look until the journal ships. Breadcrumbs inside the journal step back through history when the visitor actually came from where the crumb points — «Главная» reopens the home page at the collections block, «Журнал» reopens the index at the card they clicked — and fall back to a plain navigation when there is nothing to return to. The selector has no group headings and no scroll (every entry visible at once), each entry carries an icon and a count, its type matches the calculator buttons below (16px/600), the selected entry is marked with the hover surface plus accent-coloured label, icon and count in the light theme (a red fill there outshouted the materials themselves) and with the accent fill in dark, where that surface is almost invisible; hover must not restyle it, and the marker class is `current`, not `selected`, because a project-wide `.selected` rule forces the accent colour with `!important`; and entries with no material are hidden entirely — they reappear on their own with the first published item, so the taxonomy stays in `blog-posts.js`. Filtering never gets its own URL and needs no reset control; «Все материалы» is the reset. A rubric or filter clicked from outside the index (the article's meta line, the sidebar on an article or calculator page) opens the index with that filter already applied — carried as a one-shot intent, not as a URL. All calculator buttons, not just the yellow catalog one, carry a trailing arrow and open in a new tab so the material stays open behind them. Dates read as words inside a week — «Сегодня», «Вчера», «5 дней назад» — and as a plain date after that; the app computes the phrase in the browser while the pre-rendered page keeps the plain date, which cannot go stale. An article opens with one meta line above its h1 — rubric, a middle dot, then the date — and nothing about automation or a «Опубликовано»/«Обновлено» label. Rubric and date share the 16px size; the rubric is accent-coloured, bold, never uppercase, and links to the journal (hover underline only, no other style change). The date is the catalog's last check, never earlier than the publication day, worded as «Сегодня»/«Вчера»/«5 дней назад» inside a week; the same value feeds `dateModified`. The article h1 runs to 45px on desktop.

Blog copy preference (owner decision, 2026-08-27): article text never promises anything in the first person — no «мы проверяем», «мы подтверждаем», «мы сверяем», «мы смотрим». Blog structure preference (owner decision, 2026-08-27): inside a collection article only the cars are blocks — everything else is plain prose, because alternating callouts, compare cards and definition lists is harder to read than continuous text. A section longer than four paragraphs is either cut or split with `parts` subheadings; every article closes with a derived «Похожие статьи» block — same rubric first, then same powertrain, then the rest, as three journal cards; the list sits high on the page, right after the figures band, since that is what the visitor came for. «Топ N» belongs in some titles but not all — write the number as the `{top}` token so it can never disagree with the card count. Details in `BLOG_TEXTS_TZ.md`.
