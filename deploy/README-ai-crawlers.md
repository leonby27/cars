# Shared crawler and catalog protection

Both sites reject commercial SEO/bulk crawlers (including AhrefsSiteAudit, SERankingBacklinksBot and Semrush) before the application. AhrefsBot also supplies the Yep search engine, so it retains access under the same slow-crawl allowance rather than a full denial ([provider description](https://ahrefs.com/robot)). Training crawlers have a shared **6 requests/minute** budget per family across domains, workers and source addresses, with one extra burst request. GPTBot, ClaudeBot and meta-externalagent are training families; OAI-SearchBot, Claude-SearchBot and user-directed fetches remain separate.

Browser-looking exports cannot reset the catalog budget by changing User-Agent, query parameters, X-Forwarded-For or domain. Public collection reads allow 60/minute with a burst of 30, plus a sustained 6/minute with a burst of 30. Public vehicle/catalog reads allow 120/minute with a burst of 40. Limits apply before upstream/cache access and reply 429 with Retry-After: 10. GET/HEAD reads are covered, including normalized encoded API URLs and the BY named HTML rewrites. Account/auth endpoints, form POSTs and static build files are outside these visitor read budgets. The separate slow-crawler budget also applies at server level to stored/upstream photo locations; build assets and robots.txt do not consume it. BY robots.txt replaces the older AhrefsBot denial with AhrefsSiteAudit when served, including compressed-client requests and future builds. The server's own addresses bypass visitor budgets so scheduled warmers continue working.

Search exemptions require both a matching agent and a verified source address. Official JSON feeds cover Google, Bing, Apple, DuckDuckGo, OpenAI search/user agents, Perplexity and Anthropic search/user agents. Yandex addresses require reverse DNS under yandex.ru/net/com plus matching forward DNS; no complete cloud network or User-Agent alone is trusted. A new/unverified search address receives the generous ordinary-read allowance until verified, rather than an unconditional denial. Network refresh runs every 15 minutes, downloads feeds at most daily, reads bounded log tails for Yandex and retains previous verified data on external failures. Yandex DNS refreshes daily, with a seven-day maximum stale allowance.

Primary references: [Google verification](https://developers.google.com/crawling/docs/crawlers-fetchers/verify-google-requests), [Yandex verification](https://yandex.com/support/webmaster/en/robot-workings/check-yandex-robots), [Applebot](https://support.apple.com/en-us/119829), [OpenAI crawler roles](https://developers.openai.com/api/docs/bots), [Anthropic crawler roles and IP list](https://support.claude.com/en/articles/8896518-does-anthropic-crawl-data-from-the-web-and-how-can-site-owners-block-the-crawler), [nginx request limits](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html).

## Daily catalog enumeration guard (2026-10-03)

Both domains share a separate loopback-only Python service, `car-catalog-guard`, checked by nginx before public cache delivery. No application/customer database access or website rebuild is required. Verified search agents (matching provider IP and agent) and internal warmers are exempt. POST/HEAD, authentication, forms, analytics, images/assets and count/filter metadata are outside the daily copy budget. Public GET car/card and catalog reads share the real remote IP across domains; forwarded headers and user-agent changes cannot create a new identity.

Within a 24-hour window beginning at the first read, identical normalized reads count once. HTML/JSON requests for the same car share an identity. Tracking parameters do not create extra entries. Listing requests count requested capacity (capped at 100; HTML catalog pages count 48), not confirmed returned/saved cars. A verification is required for a new read after either (a) at least 8,000 capacity units and 100 different paginated collection reads; (b) at least 16,000 units and 300 different collection reads; or (c) 600 distinct car details. Already visited views remain available. These conservative conditions are deliberately above ordinary browsing; shared/mobile IPs can still trigger them and use visitor recovery.

A marked API 429 opens one same-origin dialog over the existing page. Its picture/audio verification restores a signed, IP-bound, one-hour cookie with an additional bounded allowance; it never resets the shared IP budget. POST forms are not intercepted, draft fields stay in place, parallel failed reads share one dialog, and closing it avoids repeated verification/retry loops. Direct HTML reads redirect to the same recovery page. Puzzle attempts are limited, expire after ten minutes and cannot be replayed; cookies are Secure/HttpOnly/SameSite and never enter public cache responses. This is a lightweight local CAPTCHA, not a claim of resistance to OCR/audio recognition, paid solvers, stolen clearance or distributed collection. No third-party customer data is sent.

Install with `python3 deploy/install-catalog-guard.py` as root from an archive containing its companion files and `catalog-guard-audio/`. The installer locks releases, backs up configs, validates nginx and restores previous files on failure. New installations start in `observe`; production was switched to `enforce` on 2026-10-03 after retrospective and live checks. Future BY/RU nginx sources use optional wildcard includes so app releases preserve this shared policy. BY proxy cache uses a new versioned key to avoid old compressed HTML without the recovery script; caches and catalog snapshots are not deleted.

Set `CATALOG_GUARD_MODE=observe` in `/etc/default/car-catalog-guard` and restart `car-catalog-guard` to stop enforcing without removing telemetry. Stopping the service also fails open: auth transport/timeouts or guard storage errors permit the original request, preserving existing crawler/rate limits. Auth requests have a 100 ms connect and 500 ms read bound. Keep the visitor recovery service and script reachable before enabling enforcement. Journald records hashed IP/counter events, never CAPTCHA answers, full query strings or customer fields; expired counters are pruned hourly.

Validation: `python3 tests/catalog-guard.test.py`, `node --test tests/catalog-guard-client.test.mjs`, and `python3 tests/catalog-guard.integration.py` (nginx required). Historical replay of 31,117 successful browser-looking reads from 5,021 addresses found four apparent exporters reaching thresholds and no other browser address. This supports the starting thresholds; it does not prove that every future real user will be exempt. Evidence and deployment receipt: `../research/catalog-protection-2026-10-03/`.

## Adaptive network and session guard (2026-10-04)

The policy's `behavior` object enables network detection independently of the temporary first-read list. Public GET reads are grouped by IPv4 `/24` and `/16`, or IPv6 `/64` and `/48`, across both domains. A group requires verification when it has at least 32 distinct addresses and 250 distinct vehicle details in an hour, or 128 addresses and 1,000 details in a day. The corresponding minimum address count also enables the existing collection-volume conditions (8,000 capacity units with 100 paginated views, or 16,000 units with 300 collection views). Windows begin at the first observed request; these are observed attempts, including denied attempts, rather than confirmed successful deliveries. Repeated normalized views count once per group/window. A detected group remains flagged for 24 hours, persisted across restarts and extended by further threshold traffic. Verified search agents and internal traffic do not enter these counters.

Eligible catalog responses also mint a signed, opaque, 24-hour `__Host-catalog_session` cookie. Its distinct-view budget follows the visitor across source-IP changes and triggers the same ordinary enumeration thresholds. The cookie authenticates its server-issued identity, not humanity; clearing it creates a different session. Host-only cookies differ between domains, while IP and network counters remain shared. Cookies are generated after the upstream shared cache; new-session responses add `Cache-Control: private, no-store` to prevent downstream shared caching of visitor identity. Authentication, submissions and unrelated metadata/assets do not mint this cookie through the guard.

After verification, additional daily allowances are stored separately from individual one-hour clearance grants. Ordinary IPs/sessions can receive at most 8,000 capacity units or 600 new details; flagged IPs/sessions receive at most 2,000 units or 100 details. Every active network group additionally shares a 10,000-unit / 1,000-detail allowance. A read is charged to each applicable scope; renewing CAPTCHA clearance, rotating IPs inside the group, clearing cookies or restarting the service cannot reset the network total. Network totals count admitted new normalized views per IP, not distinct physical cars or confirmed backend delivery. Exhausted totals produce an unmarked 429 and `Retry-After: 3600`, without opening another verification loop. Already visited views retain the existing behavior, with a valid clearance required in flagged networks.

All counts live in the guard's own SQLite database with hourly pruning; stored IP/session/network identities are keyed hashes. No application/customer database schema or data is changed. Broad/shared networks can reach these limits during legitimate use, so historical replay supports the initial settings but cannot establish zero false positives. Large proxy pools across unrelated groups, collection below every threshold, repeated update harvesting and automated puzzle solving remain possible. The four-digit local CAPTCHA is unchanged; no external challenge provider, ASN classification or browser fingerprint has been connected. The guard still fails open on service/storage failure, while existing nginx request/crawler limits remain in force.

Navigation regression verification found and fixed an existing recovery-dialog cancellation bug: an aborted request used to keep waiting for verification and could leave its dialog over a different page. Each waiting read now follows its own abort signal; the last cancellation closes the dialog, while another active read can still finish verification. Cancellation preserves `AbortError` semantics and never retries the abandoned read. Closing verification still preserves drafts and avoids retries. `node tests/catalog-guard-navigation.browser.mjs` exercises the built React client and candidate Python guard over isolated HTTPS, with no production/database requests or form submissions; use `TEST_BROWSER=webkit` for Safari's engine and `NAVIGATION_BUILD_DIR` for an alternative client/SSR build. Desktop/mobile checks cover filters, card/back, menu/login, draft preservation, browser Back during verification, picture verification in the iframe, direct HTML recovery, daily-limit refusals and the production content-security policy. Actual nginx integration additionally covers the BY named catalog/card rewrites, shared cache access and recovery frame headers.

Set `behavior.enabled` to `false` and restart the service to disable this extension while retaining configured targeted and original IP rules. To stop all daily guard enforcement, use the existing `CATALOG_GUARD_MODE=observe` switch. Adaptive detections do **not** expire with the targeted list on October 11. Validation includes signed-session continuity, tamper rejection, IPv6, parallel quota enforcement, repeated challenge renewal, slow distributed reads, real nginx/cache/recovery integration, and replay of 22,028 historical browser-looking reads. Replay detected `47.82.0.0/16`, `47.79.0.0/16`, `43.173.0.0/16` and `43.172.0.0/16`; that traffic pattern does not establish ownership or malicious intent. Publish the combined guard with the standalone installer during an explicitly authorized release; retain its backup receipt and verify the installed policy and service after installation.
